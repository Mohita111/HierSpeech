# How to Manage Documentation and Sidebars

**Important Note:** The HierSpeech repository is a speech synthesis research project. Its current source files do not include a dedicated documentation site configuration. The guidance below follows standard conventions used by documentation frameworks to help you structure and organize content if you choose to add one.

---

## 1. Adding Markdown Files

Documentation pages are created as Markdown files (files ending in `.md`) placed inside a dedicated documentation folder, typically named `docs`.

### Basic Structure

Each Markdown file becomes one page in your documentation site. You can organize pages into subfolders to create sections and categories.

For example:

```
docs/
├── intro.md
├── installation.md
├── guides/
│   ├── quick-start.md
│   └── advanced-usage.md
└── faq.md
```

In this layout, the files `intro.md`, `installation.md`, and `faq.md` appear at the top level, while `quick-start.md` and `advanced-usage.md` appear inside a "Guides" section.

### Naming and Formatting

- Use lowercase filenames with hyphens between words (for example, `quick-start.md` instead of `Quick Start.md`).
- Each file must start with a front matter block (see the next section) to define how it appears in navigation.
- Write page content below the front matter using standard Markdown syntax: headings, paragraphs, lists, links, tables, and images are all supported.

---

## 2. Front Matter for Titles and Order

Front matter is a special block placed at the very top of each Markdown file. It is separated from the page content by three dashes (`---`) above and below the block.

### Defining a Title

The title in the front matter controls what appears in the sidebar and at the top of the page.

```markdown
---
title: Getting Started
---

# Welcome to HierSpeech

This page introduces the project.
```

### Ordering Pages

You can control the order in which pages appear in the sidebar using a numeric position value. Lower numbers appear first.

```markdown
---
title: Installation
sidebar_position: 2
---
```

Pages without an explicit position are placed at the end in alphabetical order or file-system order.

### Example: Complete Front Matter

```markdown
---
title: Quick Start Guide
sidebar_position: 1
description: Learn how to set up HierSpeech in five minutes
---
```

## 3. Using a Sidebar Configuration File to Define Navigation

The navigation menu (sidebar) is defined in a dedicated JavaScript configuration file, typically named `sidebars.js` and placed in the root of the documentation site.

### Simple Manually Defined Sidebar

A basic sidebar lists pages and folders in the order you specify:

```javascript
module.exports = {
  docs: [
    'intro',
    'installation',
    {
      type: 'category',
      label: 'Guides',
      items: [
        'guides/quick-start',
        'guides/advanced-usage',
      ],
    },
    'faq',
  ],
};
```

- Each string entry (like `'intro'`) refers to a Markdown file without its `.md` extension.
- Folders are represented as "categories" with a label (the visible name) and an items list.
- The order you write entries in the array is exactly the order they appear in the sidebar.

### Using IDs Instead of File Names

Every documentation page has an identifier, usually derived from its file path. When you refer to a page in the sidebar, you use this identifier. For a file located at `docs/guides/quick-start.md`, the identifier is `guides/quick-start`.

## 4. Autogenerated vs. Manually Defined Sidebars

You have two main approaches for building your sidebar.

### Autogenerated Sidebar

An autogenerated sidebar automatically includes every Markdown file found in the documentation folder, organized by folder structure.

```javascript
module.exports = {
  docs: [
    {
      type: 'autogenerated',
      dirName: '.',
    },
  ],
};
```

**Advantages:**
- No need to update the sidebar file every time you add a new page.
- New files and folders automatically appear in navigation.
- Folder names become category labels automatically.

**When to use it:** Ideal for large documentation sets that change frequently, or when you want to minimize configuration effort.

### Manually Defined Sidebar

A manually defined sidebar gives you complete control over which pages appear and in what order.

```javascript
module.exports = {
  docs: [
    'intro',
    'installation',
    'guides/quick-start',
  ],
};
```

**Advantages:**
- You decide exactly what appears and what is hidden.
- You can rename categories independently of folder names.
- You can reorder pages without moving files.

**When to use it:** Ideal for small, curated documentation sets where every page matters and the intended reading order is important.

### Combining Both Approaches

You can mix both styles. For example, automatically generate a "Reference" section while manually defining the main navigation:

```javascript
module.exports = {
  docs: [
    'intro',
    'installation',
    {
      type: 'category',
      label: 'API Reference',
      items: [
        {
          type: 'autogenerated',
          dirName: 'api',
        },
      ],
    },
  ],
};
```

## 5. Versioning Documentation

Versioning lets you keep documentation for older releases available alongside the current version, so users can access guidance that matches the software version they are using.

### Creating a New Version

When you release a new version of your project, you create a snapshot of the current documentation. This snapshot is stored separately and remains accessible even as the main documentation evolves.

The process typically involves:
1. Making sure the current documentation is complete and accurate.
2. Running a versioning command that copies all current pages into a versioned folder named after your version (for example, `version-1.2.0`).
3. The current, unversioned documentation (usually labeled "Next" or "Current") continues to receive updates.
4. The versioned copy is frozen and serves as a historical record.

### Version Dropdown

Visitors see a dropdown menu in the documentation header that lets them switch between available versions. They can choose:
- The latest stable version (recommended for most users).
- An older version (for users who have not yet upgraded).
- The "Next" or development version (for previewing upcoming changes).

### Marking Versions as Deprecated

When a version is no longer supported, you can mark it as deprecated. Users will see a warning banner indicating that the version is outdated and that they should consult a newer version.

### Best Practices for Versioning

- Version documentation at the same time you tag a new software release.
- Only version documentation that is stable and tested.
- Keep the number of active versions small to avoid confusing users.
- Provide a clear "latest" label for the current recommended documentation.
- Use release notes or a changelog page to summarize what changed between versions.

## Putting It All Together

A complete documentation setup involves these steps:

1. **Create your content:** Write Markdown files inside the documentation folder, organized into subfolders as needed.
2. **Add front matter:** Give each file a title and, optionally, a position value to control ordering.
3. **Configure navigation:** Define a sidebar file that lists pages and categories in the order you want, or use autogeneration for simplicity.
4. **Version your docs:** Create version snapshots at each release and mark old versions as deprecated when appropriate.
5. **Test and publish:** Preview the documentation site to confirm that pages appear correctly and navigation works as expected.
